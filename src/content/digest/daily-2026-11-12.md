Of 380 agent runs that returned the right numbers on a financial research benchmark, 193 got there by reading data the analyst could not have seen on the date in question. That is 50.8%, and it comes from [BuySideFlow](https://arxiv.org/abs/2611.12966), a benchmark of 408 practitioner-derived investment research tasks built on a fixed snapshot of a licensed production financial database. Nine agent configurations scored between 16.2% and 36.8% on result accuracy, which is already low, but the more useful finding is the audit: expert review of 900 executed workflows on 100 shared tasks showed that a matching answer says almost nothing about whether the agent respected disclosure cutoffs or picked the right historical record version. Point-in-time validity is a time-semantics problem, the kind a governed semantic layer is supposed to encode once, and this paper gives a clean number for what happens when the agent has to infer it from raw tables every run.

The same pattern, outcome checks hiding behavior that matters, runs through most of what landed in the last day.

## Instruction files rot, and agents follow them anyway

A study of [stale instruction files](https://ui.adsabs.harvard.edu/abs/2026arXiv261109802M) took three real stale instructions from active open-source repositories (a test command, a code location, and a procedure for adding a component) and ran 22 maintenance tasks under three conditions: stale, corrected, and removed. Across 732 trajectories from two models, analyzed at the tool-call level, agents acted on stale guidance whenever it was relevant to the task, sometimes even when correct information sat elsewhere in the repo. On the stale test command, Claude Sonnet 5.5 spent about two extra tool calls per run, a third more than with the corrected command. Agents generally recovered from the immediate failure, and not one of them fixed the instruction file. Correcting the file eliminated operations on obsolete paths; deleting the bad instruction prevented most of them. The authors frame this as documentation debt whose interest is charged to every future session, which is the right frame for anyone maintaining a CLAUDE.md across a team.

A companion paper asks the inverse question: when the instruction is current, [do agents actually follow it](https://arxiv.org/abs/2611.13709)? The authors mined real AGENTS.md-style context files, linked them to agent-authored commits, turned the explicit instructions into executable measurement scripts, and scored compliance per instruction. Agents comply more often than not, but adherence splits sharply: some instruction categories are followed consistently and others are never respected, and the split differs across coding agents. That bimodal shape is actionable. It says which rules belong in the context file and which need a hook, a linter, or a CI gate behind them.

Google engineers Sam Saccone and Madhuri Garikapati described a third form of the same failure, which they call [agent distraction](https://www.infoq.com/news/2026/11/google-agent-distraction/?utm_campaign=infoq_content&utm_source=infoq&utm_medium=feed&utm_term=global): old TODO comments, references to long-closed bugs, and outdated specs pull coding agents into unrequested side quests. Taken together with the stale-file study, the lesson is that agents treat everything in the repo as live guidance, so technical debt now has a per-session token cost on top of its usual maintenance cost.

## Failure predictors mostly predict the issue

[Hard Issue, Weak Model, or Bad Run?](https://ui.adsabs.harvard.edu/abs/2026arXiv261108285S) takes apart trajectory-based failure prediction for SWE agents, the kind of monitor that reads a partial run and decides whether to stop, retry, or switch models. On public SWE-bench Verified trajectories, a reference score that never looks at the run, only at how hard the issue was for other models, reaches 0.92 AUROC; trajectory predictors reach about 0.62. Within an issue, simply knowing which model ran beats the predictors, and once difficulty and model ability are accounted for, what the trajectory adds is statistically equivalent to zero. The best-single-model versus any-model-oracle gap that motivates model switching is no larger than random variation, and per-issue switching gains nothing on held-out runs. A repeated-run pilot shows the same model often solves an issue in some runs and fails it in others, so retry has real room, but only for bad runs, and current predictors cannot tell a bad run from an issue beyond the model's ability. Anyone building retry or escalation policy on top of a trajectory classifier should read this before trusting the classifier's AUROC.

## Delegation is a measurable skill

[WorkflowArena](https://ui.adsabs.harvard.edu/abs/2026arXiv261112856J) benchmarks what it calls workflow orchestration: 145 long-horizon tasks across 8 domains, from software engineering and formal math to legal analysis and 3D production, where the agent decides whether and how to spawn workers and every delegation is logged. Nine models, no single best configuration across domains, and visibly different styles: at high effort, Claude models in Claude Code invoke workflows less often but with larger worker groups, while GPT models in Codex delegate more often in smaller units. The controlled result is the strongest part. With the executing model held fixed on a hard subset, workflows authored by Claude Opus 5.5 substantially improved weaker executors, which separates planning quality from execution quality in a way end-to-end benchmarks cannot.

## Finding the right table before writing any SQL

For enterprise text-to-SQL, [NIFT-SQL](https://arxiv.org/abs/2611.12731) attacks the step before generation: picking the tables a question needs out of schemas with 244 to 971 tables. It fuses hybrid search over a retriever fine-tuned on each customer's example questions with a fine-tuned 560M cross-encoder that scores every table for necessity, combined through a logistic regression. Measured as the share of questions where every reference table lands in the top 15, it reaches 69.2%, 89.5%, and 85.6% on BEAVER, LiveSQLBench, and LiveSQLBench-Large, against 30.4%, 41.0%, and 21.8% for plain hybrid search. It reads only table names, column names, and declared keys, so the gain comes from customer-specific supervision rather than richer metadata. The paper also reports its own weak spots: on a newer BEAVER release, NIFT-SQL trails the label-matched retriever at top 15 on real questions.

## What to watch

BuySideFlow and the stale-file study both report outcome checks that pass while the process underneath is wrong, and both supply the audit methodology to catch it. The open question is whether either kind of check becomes cheap enough to run in CI. A point-in-time validator that sits between the agent and the warehouse, or a lint that flags context-file paths that no longer resolve, would turn these papers into gates. Whoever ships the first one gets to find out how much of today's passing agent work survives it.
