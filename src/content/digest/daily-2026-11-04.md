Ten coding agents finish 95% of requests handed to them one at a time and 51% when the same requests arrive as a chain of twenty, each built on the last. That gap, from [Built on Broken Assumptions (BOBA): Why Coding Agents Cannot Be Left Alone](https://arxiv.org/abs/2611.02207) by Alejandro Cuadron and Arpit Gupta, is the sharpest number in a day of papers that keep landing on the same failure: work that runs, passes the check in front of it, and is still wrong.

BOBA-Bench strings together 280 chains of 20 consecutive requests from 140 real open-source projects, and the authors rule out the obvious explanation first. Agent-written code, once checked, is nearly as good a base for later requests as human code, so the chain does not break because agents write worse code. It breaks because an agent declares a request done when its own tests pass, those tests miss a mistake, and the next request builds on broken code and fails about twice as often. The mistake is rarely found later. Asking agents to review an implementation for correctness does not catch it either; they are right 53% of the time. The intervention that works is small and external: one "that's wrong" after a failed request plus a single repair round lifts chain completion from 51% to 59%, and a repaired mistake stops contaminating the requests after it. For anyone running agents unattended against a backlog, the paper turns "keep a human in the loop" into a measurable claim about where the verification signal has to come from, and it rules out the agent's own test suite as that source.

[Do Coding Agents Catch Their Own Bugs? (They Don't.)](https://arxiv.org/abs/2611.01181), from Shaswat Patel, Valerie Chen and coauthors, measures the neighboring gap. Foresight-SWE has 212 samples across 4 languages and 35 popular repositories, each a pull request paired with the later PR that fixed a defect the first one introduced. Its foresight resolve rate counts an instance only when the agent completes the original task and also avoids the defect the follow-up had to fix, and across eleven models it runs from 6.13% to 24.53%. Read next to BOBA, the two papers describe one agent from two sides: it does not anticipate the problem nobody asked about, and once the problem is in the code it does not notice. A review tool that only checks whether a diff does what the ticket said will miss both.

[Do Agents Still Follow the Rules?](https://arxiv.org/abs/2611.03223) by Yiwei Zha, Herbert Bos and coauthors moves the question inside the harness. ARCBench, built on the open-source pi agent harness, scores rule compliance from the tool calls an agent makes after its history is compacted, and the result cuts against the usual fix. Compaction rarely deletes the rule; most post-compaction violations happen while the rule is still in the summarized history, with the agent reading a later request as permission and proceeding. How the rule is delivered decides whether the agent would break it even without compaction, while the compaction strategy and budget decide whether the rule survives. Compacted runs that keep the rule still violate it more than twice as often as runs with the full history, and the strongest attack on the compactor, which corrupts the rule inside the summary, more than doubles violations. Pinning rules into the summary handles the smaller half of the problem.

The analytics papers make the same argument about meaning. [Text-to-SQL Models Make Choices Without Saying So](https://arxiv.org/abs/2611.04318), from Yichen Xu, Shipei Lin and Chenhao Ma, builds SpecBridge around calculation choices a request leaves open, such as counting rows versus distinct entities. Each test poses three otherwise identical requests, one leaving the choice open and one per interpretation, all scored by execution against real databases. On 204 hand-validated tests, four models usually compute each interpretation when it is spelled out, yet for the open request they return both in only 15 to 58% of the cases where they could, often without mentioning that a choice existed. The models can do the computation and fail to report the decision, and benchmarks reward that silence: on BIRD questions where such a choice changes the answer, more than two in five answers marked wrong are correct under the other reading. The fix needs no stronger model. Decide first whether the request is open, then answer each interpretation in its own call; that raises full-coverage answers by 29 to 63 points over the single answer production assistants give, holds precision on clear requests, and takes fewer user turns than a clarifying question.

[Verifying Text-to-SQL Queries under Changing Business Semantics](https://arxiv.org/abs/2610.41090), by Genliang Zhu and coauthors, asks what happens to a correct query after finance changes the definition underneath it: refund attribution, tax treatment, the eligible population, the exchange-rate date. Their executable verification profile binds a requested definition revision and knowledge cutoff to legal counterexample data and exact monetary comparison. In a preregistered run over 32 newly authored revision families, 144 of 192 query-definition cells fail to conform to the revised definition, and 63 of those 144 still agree with the correct query on the current data snapshot, so a spot check against today's numbers would pass them. With a budget of eight counterexample ledgers, obligation-guided checking finds 137 discrepancies against 127 for generic ordering, a paired difference of 6.9 points (95% interval 2.1 to 13.6, p = 0.0156), and no arm rejects any of the 36 conforming cells. The benefit traces to coverage rather than to prioritizing the revised obligation, which tells anyone building such a check that breadth of counterexamples does the work. The claims are scoped to an authored schema and local models, but the 63-of-144 figure is reason enough to stop treating a matching number as evidence that a governed query still means what it did.

The practitioner version arrived on r/LLMDevs, where [a post on BI for agents](https://www.reddit.com/r/LLMDevs/comments/1xmxpue/bi_for_agents_your_analytics_agent_is_probably/) walks through Cube's write-up of the agentic analytics harness it runs on its semantic layer. The headline bug is mundane: a query returns 50,000 rows, the tool passes back the first 100 without saying so, and the agent ranks and sums one page and reports it as the total. Cube's tool returns the page with the total row count, a query id for fetching more, and an explicit partial-result note. The rest of the list is that failure in other shapes, covering errors that tell the model how to recover, success states that separate "ran" from "saved" and "zero rows" from "done", semantic-model search that refreshes on every read and filters by the caller's access instead of a preloaded schema that goes stale at the next deploy, and SQL against governed views where the agent composes `measure(revenue) / measure(order_count)` without redefining either measure. The poster's closing question belongs in every analytics eval review: most eval sets use questions whose answers fit in one page, so the summed-partial-result bug never fires.

Each of these teams had to build its own instrument to see the failure, whether chained requests, paired pull requests, compaction measured inside a working harness, triplet prompts, revision ledgers, or a table larger than the page size, and none of those instruments appears in the benchmarks most teams report. Watch for the first agent harness or semantic layer that reports one by default, chain completion beside single-task pass rate or an ambiguity count beside execution accuracy, and for whether its number looks closer to 51% or to 95%.
