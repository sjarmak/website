In 79 of 80 runs, Claude Code read a project's instruction file, noticed that it contradicted the code, said so, and then did what the file said. That result comes from a 320-run study by Xu and Wu, and it frames most of this week's reading: agents defer to whatever state they inherit, and most of our benchmarks never put them in a position where that deference costs anything.

## Instruction files outrank the code they describe

Xu and Wu paired 40 Python projects with stale instruction files and ran Claude Code and Codex CLI against them 320 times. Without intervention, 90.1% of the agents' choices followed the stale file over the code. The two tools failed differently: Claude Code flagged the conflict in 79 of 80 runs and complied with the file anyway, while Codex rewrote code to match the file in 20 of 80 runs, after which tests failed in 17. The authors' explanation is about channels. The instruction file reaches the model as an instruction, the code reaches it as tool output, and models rank tool output lower. One added sentence moved code-following from 4.2% to 91.4% and the test pass rate from 89.4% to 100%, which makes it the cheapest fix in this week's reading. If your AGENTS.md or CLAUDE.md changes less often than your code, take the exact wording from the paper and try it. [Stale Instruction Files Override the Code in Coding Agents](https://arxiv.org/abs/2610.30571)

The Claude Code half worries me more than the Codex half. A rewrite that fails 17 test runs gets caught, while a transcript that names the contradiction and then follows the wrong source reads as careful work to anyone skimming it, so the flag itself becomes false reassurance.

## Agents lose 20 to 53 points when the workspace is not clean

SWE-Residual builds 198 residual starting states from 111 DeepSWE and Terminal-Bench tasks, so the agent begins in a workspace that earlier work has already touched. Across five frontier agents, success fell by 20.6 to 53.5 points on DeepSWE and by 20.6 to 34.9 points on Terminal-Bench, and the DeepSWE ranking reversed. The authors name the mechanism acceptance bias: between 58.9% and 88.2% of failed DeepSWE runs submitted with the same tests still failing. I read that as the instruction-file problem applied to repository state, where the agent treats whatever it inherited as the baseline. [SWE-Residual](https://arxiv.org/abs/2610.25899)

SWE-Shift changes the workspace during the task instead of before it. Its 120 scenarios cover 12 change families inserted at 9 positions, and all 17 systems tested scored lower when shifted. GPT-6 Astra fell from 67.35% to 24.79%, with paired success at 20.34%. Two families produced zero paired success for every system: changes to tools or the session, and stale evidence. Anyone who adds or removes MCP servers mid-session, or runs long sessions against a shared repository, is already working inside those two families. [SWE-Shift](https://arxiv.org/abs/2610.32196)

JetBrains Research came at realism from usage logs. Igor Slinko's post analyzes 4,782 sessions and about 14,000 messages: 50.9% were a single message, 33% ran to three or more, and bug fixes (26%) outnumbered features (19%). SWE-Bench Pro leans the other way, at 55% features, 39% bugs and 6% refactoring. Their SWE-TaskFlow rebuilds 700 SWE-Bench Pro tasks (31 of 731 were dropped), splits each one three ways, and adds repository questions backed by proof scripts, which raised the paper's alignment score (TFAS) from 59.6 to 77.8. Splitting raised per-task cost 2.0 to 2.6 times; the resolve rate held flat for GPT-5.6 Terra and fell 4 to 5 points for the other models, while a Concat control matched the single-message baseline. The 454 questions across 255 tasks added 4% to 24% to cost, with answer accuracy from 69.8% (GPT-5.4 Mini) to 83.0% (GPT-5.6 Terra). The paper, headed to a NeurIPS 2026 workshop, concludes there is "no universal realistic coding-agent benchmark," and the dataset is on Hugging Face as JetBrains-Research/SWE-TaskFlow-SWE-Bench-Pro. [Coding-Agent Benchmarks Should Match Their Users' Task Flows](https://blog.jetbrains.com/research/2026/10/user-task-flow-paper/)

## Graders check what the task never said, and agents miss when to stop

Fei Ding's audit asks what a test-graded benchmark checks that its specification never stated. The audit runs at 89.2% precision and 92.9% recall. On SWE-Milestone, 25 of 98 milestones had such gaps; affected units failed in 80.6% of runs against 48.4% for the rest, and a single withheld name broke compilation in 126 of 128 cases. Rankings held, but scores shifted, and the benchmark ended up rewarding agents that reproduced upstream names. When the specification is release notes or an LLM-written summary, a third or more of tasks are affected, which is a direct warning to anyone generating eval tasks from commit history. [What the Specification Did Not Say](https://arxiv.org/abs/2610.30635)

ImpasseBench measures the moment an agent should stop. Across 12 blockers, 8 models and 19,371 trajectories, a third of runs used up their budget after they already had enough evidence to know they were stuck, and every unsafe request in the data came after that point. An escalation tool cut budget exhaustion from 34.0% to 6.7%, and a monitor nearly tripled success after restoration. The weak spot is the handoff: escalation tickets named the blocker but left out progress and verification status, which is exactly the kind of residual state SWE-Residual shows the next agent accepting without a check. A ticket template with required fields for both costs a few lines of harness code. [Knowing When to Stop](https://arxiv.org/abs/2610.31895)

## Reliability lives in the code around the model

Marla and Bhatnagar split a retry into four obligations: a checkpoint, permission to dispatch, evidence of the effect, and permission to reconcile. They ran 336 histories on LangGraph and Temporal (14 schedules, 3 provider contracts, 4 policies), and all 168 paired cells came out identical across the two engines. The policy is what moved results. Reconciliation against a retained ledger passed 42 of 42 cases (21 completions, 15 denials, and 6 unknowns with the reservation retained), against 30 for cached retry, 36 for revalidation and 31 for stable keys. The paper closes with a 16-case study on Arya.ai's InfinityOS. If your agents move money or send messages, design for those six unknowns first, because guessing on them either duplicates an effect or drops it. [Permission to Retry](https://arxiv.org/abs/2610.31916)

Meta's engineering team describes an agent system for onboarding data columns across 3 repositories and 3 languages, with up to 6 stages per change, built around a 1,300-line router, 20-plus workflows and 14 subagents. A single agent reached 70% to 80% success with per-task prompts and 10% to 20% without them. The architecture takes the procedure out of the model: a 7-step protocol in which only step 6 calls an LLM, workflow templates written as state machines, and more than 25 knowledge files loaded on demand. Migrating a pipeline needed zero new agent code. Configuration prep went from 3 to 4 days, to about a day, to under an hour, and about two-thirds of changes land without significant human edits. The post also cites a Mount Sinai preprint reporting 65.3% versus 16.6% at 80-task batches with up to 65 times fewer tokens. Read next to Xu and Wu, the per-task prompt numbers say the written procedure carries most of the weight in both directions. [The Thin Orchestrator](https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent-architecture/)

## Governed analytics needs evidence a reviewer can check

Adversarial Intent Resolution (AIR) handles ambiguous questions by generating competing interpretations, executing them to confirm they actually differ, and asking a clarification question grounded in the data, all without training. On AMBROSIA with schema only, it scored F1 0.679 against 0.618 for IntentRL, and it lost about 7% without the full database where IntentRL lost about 20%. It also posted higher F1 on AmbiQT, where the ambiguity comes from schema design, in both settings. The idea worth taking into a semantic layer is the trigger: ask the user only when two readings of the question return different results. [Probing Ambiguity](https://arxiv.org/abs/2610.24248)

EquiTrace builds SQL equivalence proofs out of query rewrite rules. It proved 648 of 1,106 text-to-SQL pairs (58.6%), 229 of 266 curated pairs (86.1%) and 97 of 240 LLM rewrites (40.4%); on that last set, QED proved 35 and SQLSolver 38. An analysis of 1,242 proofs shows coverage resting on a handful of rewrite rules, and every proof can be replayed. A replayable proof that a generated query matches a certified definition is evidence you can store next to the query and re-check after a schema change, which an execution match on a sample database cannot give you. [Building SQL Equivalence Proofs from Query Rewrite Rules](https://arxiv.org/abs/2610.30100)

Akhtar and Freeman apply the same instinct to metadata. In their contestable-governance design, specialist agents produce scored, cited arguments for disputed metadata decisions, a steward can accept, reject, modify or add arguments before commit, and a governance record keeps the evidence, the interventions and the outcome. A versioned domain glossary feeds the agents model-specific terms and acronym definitions, a triage path saves full argumentation for uncertain proposals, and a gate controls which verified decisions become precedent. This is a design paper with two HVAC use cases, point classification against Brick Schema class labels (with an open reference implementation) and an illustrative warranty failure-mode decision, so there are no benchmark numbers to weigh. The problem statement is the part to keep: a perfunctory approval leaves no record of what the reviewer checked. [Contestable Agents for Data Governance](https://arxiv.org/abs/2610.31553)

## Higher evidence coverage did not produce the best answers

The long-document RAG study compares 11 configurations on 396 QASPER questions and 80 questions from 8 textbooks, with a 5-passage limit. On the textbooks, Hybrid+Jev covered 94.1% of the evidence, a Jev full scan 88.7%, and OpenAI dense retrieval 81.3%. Coverage did not settle answer quality, though: Hybrid+Decisions had the best answer accuracy, 0.892, despite lower coverage. Full scans pay in latency on every query and dense retrieval costs less to reuse, so the right choice depends on how many times a document will be asked about. [Scan or Index?](https://arxiv.org/abs/2610.28957)

## What to watch

Most of these papers measure agents trusting state they did not create: an instruction file, a half-finished repository, evidence gathered several steps back, a retry whose first attempt may already have landed, a question taken at face value. The fixes that worked were small and structural (one sentence, an escalation tool, a retained ledger, a state machine around a single model call, an execution check before a clarifying question), and none of them required a stronger model. Over the next few months, watch whether benchmark maintainers adopt residual and shifted workspaces as default conditions, since until the leaderboards people cite include them, published scores will keep describing agents that start every task in a clean checkout. In the meantime, open the instruction file in your busiest repository and count the lines that are still true.
