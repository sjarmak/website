Across 360 controlled trials in which a repository's existing code contradicted a coding agent's default way of implementing something, the agent copied the repository 359 times. That is the opening number in [Precedent or Intent? What Coding Agents Follow When Evolving Existing Code](https://arxiv.org/abs/2610.38244), from Zhu, Xu, Yang, Wang and Zhang, who ran 5,625 trials across four coding agents and six pairs of functionally equivalent implementations, then checked the results in four open-source repositories spanning three languages. The agents start from the same defaults, and precedent overrides them almost every time. Which precedent counts is the sharper finding: three supporting files next to the edit site produced 96% adoption, the same pattern in sibling-resource files produced 4%, and moving files around with the example count held fixed swung adoption between 0% and 100%.

The practical case is a task that deliberately breaks with the past, such as a migration off an old pattern. Code examples alone got 38 of 60 joint successes for two agents on two implementation pairs; a written priority rule got 59 of 60. In the open-source repositories the gap was wider, with a rule loaded by the harness lifting joint success from 0 of 120 to 117 of 120. The authors argue for design-decision traceability, recording why a choice was made and when it should yield, because the code records only the choice. For anyone maintaining a CLAUDE.md or AGENTS.md, this is a measurement of what those files are worth when they state priorities, and of how badly an agent misreads a migration when they stay silent.

That same trust channel is the subject of [Security Impact of Coding Agent's Memory Files](https://arxiv.org/abs/2610.38521) by de Moura, Güler and Noller. Anyone who can land a pull request against CLAUDE.md can steer the agent without touching the developer's prompt, so the authors wrote two malicious memory files for each of 12 CWE classes, one framing the removal of defensive checks as engineering best practice and one demanding it outright, and ran Claude Code on Sonnet 5.5 plus OpenCode on Qwen 3.8 27B and DeepSeek V4.1 Flash against 36 SecRepoBench tasks. Secure completions moved between minus 8 and plus 6 percentage points with no consistent direction, which at 36 tasks is inconclusive rather than reassuring. The disclosure result is the one to act on: Claude Code named the memory file in about two thirds of its final messages, while OpenCode mentioned it almost only in its reasoning trace, which the developer does not read. Agents that flagged the file as an attack still produced vulnerable code, so recognition inside the model is not a defense.

The two papers are less contradictory than they look. A priority rule about which of two valid implementations to use moves behavior enormously; a file asking the agent to drop input validation plausibly runs against safety training and moves it a little, erratically. The case I would want measured next sits between them, a plausible rule that steers implementation choices toward a weaker library or pattern and reads like ordinary team convention.

[When Relevant Code Is Wrong: Runtime-Aware Context for AI Coding Agents](https://arxiv.org/abs/2610.38800), by Assunção and Periyathambi, comes at precedent from the retrieval side. A retrieved snippet can be the most similar artifact in the repository and still describe code behind a disabled feature flag, code superseded by a migration, or code incompatible with the deployment being changed. They call the missing criterion operational context validity and build CASE, an agent-agnostic layer that joins repository artifacts to runtime configuration and architectural history, labels each piece of evidence valid, invalid or unknown, and packages actionable guidance separately from historical rationale. The evaluation is small (six tasks, 15 artifacts, three deployments), and the authors say it shows feasibility, not better agent correctness. Conventional retrieval surfaced 16 incompatible artifact occurrences as actionable; CASE excluded all of them while keeping every applicable artifact. Recency filtering cut valid recall to 0.43, and stripping feature-flag evidence out of CASE cut it to 0.13. Next to the precedent paper's 0-to-100% swing from file placement, that is a direct argument for putting deployment state into the ranking for coding-agent retrieval, alongside similarity and recency.

The semantic-governance version of the problem appears in a revised [Executable Schema Contracts: From Automatic Ingestion to Multi-Source Retrieval](https://arxiv.org/abs/2606.05415) from Jonnalagedda, Yao, Gao, Hasson and Das. The system discovers an executable schema from raw tables, documents and semi-structured files and uses it as the contract for both knowledge-graph construction and query-time retrieval. A closed-world field catalog restricts the LLM to fields attested in the data; deterministic structural analysis, not the model, infers identity keys, foreign keys and source hierarchy; and at query time the schema, extendable only through a monotonic protocol, routes a multi-tool agent between structured lookup, graph traversal and vector search, with citations traceable to source. The abstract reports gains over retrieval-only and decomposition baselines on four QA benchmarks, with ablations crediting each component, but gives no effect sizes, so check the full paper before quoting any. The split is the part worth copying: the model proposes meaning, deterministic code fixes identity and joins, and the contract can grow but never silently change.

Between agents the trust problem is starker, and [PCM: A Proof-Carrying Message Protocol for Verifiable Multi-Agent Communication](https://arxiv.org/abs/2610.39109) from Bravish Ghosh at Cygnux Labs proposes a fix. A2A and MCP authenticate the channel, but when one agent tells another that the tests passed or a human approved a refund, the sender is the party in doubt. PCM makes every claim carry evidence: records from an append-only Merkle log the agent cannot write, inclusion proofs, and a signature from an attester the agent does not control. Receivers check offline and return proven, unproven or failed, and a claim resting only on the agent's own report is never proven. Authority travels as grant chains rooted in a recorded human approval, and the chains can only narrow. On a pre-specified set of 926 messages from real runs, 712 of them lies in 16 classes, PCM accepted 10 lies, all stale evidence (1.4%, 95% CI 0.8 to 2.6%). Plain A2A accepted all 712, and models of six deployed protocols, including A2A with signed Agent Cards, SCITT and AP2, accepted 504 to 712. Two independent verifiers agreed on all 926 verdicts at about 1 ms each. It is a single-author paper with an author-built benchmark, and the stale-evidence gap needs a freshness rule, but "never proven on self-report" is the right default for any orchestrator that lets a subagent mark its own work done.

One team running that principle posted its numbers to [r/ClaudeCode](https://www.reddit.com/r/ClaudeCode/comments/1xirdgs/i_counted_where_our_claude_code_agents_get_sent/). Every story passes through separate Claude Code sessions for tech design, implementation, a CI read, a diff-versus-acceptance-criteria check and a browser walk on staging, and the session that wrote the code never marks it done. Over 10 weeks, about 21,000 sessions and 1,349 stories, roughly 4,400 repeat implementation passes followed CI (55%), the criteria check (25%), the staging check (8%) and tech design (6%). When a story failed CI twice with a named test both times, it was a different test about 85% of the time, which points at fixes breaking neighbors rather than agents missing log output. CI generated most of the rework, but the criteria check generated the cost. The top 10% of stories by spend needed more than twice the passes at about 5x the cost per pass, and the criteria check bounced 58% of them at least twice against 12% of the rest, while CI bounced both groups at about the same rate (40% versus 39%). The poster's fix, splitting big stories before implementation so the criteria leave less room for a second reading, is the priority-rule result in another form: ambiguity nobody resolved in writing gets resolved by the agent, one expensive pass at a time.

JetBrains' [Junie Eco Mode](https://blog.jetbrains.com/junie/2026/10/junie-eco-mode/) bets on writing the decision down once. The selected model investigates read-only for about 15 steps and writes a fixed-structure plan (goal, scope, where to change, approach, tests, risks), then hands the conversation to GPT-6 Luna for the edit-build-test loop, with one handoff per task and no calls back up. Across 29 paired configurations on one internal benchmark, average cost per task fell from $2.61 to $1.11 while resolve rate moved from 49.1% to 48.5%; on a large-repository benchmark of 21 pairs, cost fell from $2.51 to $1.30 with resolve rate flat at 32.1%. Opus 5.5 at max effort went from 55% at $4.91 to 56% at $1.81 on a 100-task slice. These are private benchmarks reported by the vendor, which notes that individual configurations move more than the averages, so the per-configuration spread is the number to ask for.

The next thing to watch is whether harnesses load design rationale and priority rules as first-class context, the way they load tool definitions now, and whether anyone reruns the memory-file attack with a rule subtle enough to pass for team convention. If the precedent numbers hold, the instruction file is the strongest lever in the repository, and the memory-file results say it deserves the review a code change gets.
