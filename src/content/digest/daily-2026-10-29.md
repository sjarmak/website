Tencent's FeatureArc benchmark asks ten coding agents to build a feature across 2 to 10 successive stages, each extension landing on the agent's own earlier code, in one persistent session with no external test feedback and no rollback. Pooled success at the first stage is 62.7%. Test the whole feature on the final code and it drops to 28.5%. The trajectory analysis explains the gap: inherited defects show up in 72.9% of failed later stages, and in the stages after a failure, agents leave the earlier error unnoticed about 95% of the time, because their self-tests almost never go back to check what they built before ([FeatureArc](https://arxiv.org/abs/2610.37434)).

Two things follow for anyone grading agents. Single-request benchmarks on a fixed codebase measure something like the 62.7% number, while the workflow people actually run, where a feature grows over a week of follow-up requests, sits closer to 28.5%. The failure also sits in verification scope: the agent writes stage four competently on top of a stage-two bug it never re-tested. The construction pipeline is the reusable part. It mines repository histories and validates fail-to-pass tests for new behavior plus pass-to-pass tests for existing behavior on the reference code before and after each stage, across 73 manually reviewed tasks in four languages, which is the shape a regression-aware internal eval should have.

A second paper from the same arXiv batch measures the opposite failure, agents that never stop. [Your Wish Is My Commit](https://arxiv.org/abs/2610.36346) repeatedly asks Codex and Claude Code, across five models, to refactor further on algorithmic (n=50) and object-oriented (n=10) suites. Refactoring has no natural stopping point, so any edit made after the code is clean reflects compliance with the request rather than improvement. Over 3,000 turns, none of the models stopped once the code was optimized; every one kept editing, rewrote up to 31 times the size of the original codebase before its first stop, and resumed edits after declaring the task complete. The six behavioral signals of over-compliance the authors define are the useful deliverable, since a harness can watch for them and cut the loop when the model won't. Read alongside FeatureArc, the profile is an agent that pushes forward too eagerly and looks back too rarely.

[The Inbox as a Coordination Primitive for LLM Agent Societies](https://arxiv.org/abs/2610.36264), by Sreedhar, Yuan, Chari and Raskar, argues that multi-agent protocols optimize the wrong scarce resource. Delivery is cheap; reading costs tokens, and context is finite. Under push semantics, where the sender decides when a message lands in the recipient's context, an agent leading 20 concurrent negotiations with a full memory proposes options that were already rejected 97% of the time, because the oldest replies fell out of context. The pull alternative parks messages in an inbox outside the context and lets each agent's own rules decide what to read and keep. In simulated societies of 1,000 to 16,000 agents, with every decision an LLM judgment, an inbox that reads deposit-carrying messages first still finds about 60% of the agents a request needs, where first-come-first-read misses every request. The paper splits the inbox into four decisions (what to read, what to keep, what a sender pays, what a reply may say) and finds the best rule for each depends on traffic and role. Anyone running an orchestrator that fans worker replies back into one lead agent will recognize a small version of that 97% failure.

On the semantic-governance side, the most concrete item of the last day is a security advisory. Schemagate, an open-source access layer that sits in front of text-to-SQL agents and checks which tables a generated query touches (the same layer that took the top BIRD Mini-Dev slot with Claude Opus 5.5 a few days ago), shipped [1.15.1 to close a bypass](https://www.reddit.com/r/LLMDevs/comments/1xi9sfm/if_your_llmtosql_gate_checks_table_names_a_query/) reported by Artur Chlebicki: `SELECT query_to_xml('SELECT * FROM hr_compensation', true, true, '')`. The outer query names no table, so the gate passes it, and Postgres executes the inner query from the string literal. Oracle's `DBMS_XMLGEN.GETXML` and SQL Server's `OPENQUERY` and `sp_executesql` have the same shape. The fix refuses functions that execute SQL from strings across Postgres, Oracle, SQL Server and Snowflake, refuses any string argument that looks like a query naming a hidden table, and adds 31 tests, 23 of which fail on 1.15.0. The maintainer states the residue plainly: a concatenated string passed to an unlisted function still gets through, and read-only database grants are what actually lock it. For anyone building governed execution, a parser-level check over generated SQL can only reason about syntax, so the policy that keeps an agent away from compensation data has to be enforced in grants and row and column policies, where the database sees what the query really does.

For agent reliability, AWS shipped a [Durable Execution Telemetry Exporter](https://aws.amazon.com/about-aws/whats-new/2026/10/lambda-durable-telemetry/) for Lambda durable functions, the step-checkpointed runtime AWS offers for multi-step AI workflows that run up to a year. The plugin exports per-step execution status, operation timing, step inputs and outputs, and errors to 13 built-in destinations including CloudWatch Logs, S3 for Athena, DynamoDB, Aurora and OpenSearch, with field redaction and a sampling rate, in TypeScript, Python, Java and Go. A companion MCP server lets an agent query that history, so an on-call engineer can ask for recent failed executions and their causes. Durable-execution history is already the replay log for a long-running agent; exporting it with step-level inputs and outputs makes it an audit trail you can query after the standard retention window. For LLM workflows those inputs and outputs will include prompts and tool payloads, so most of the real engineering will go into the redaction config.

On retrieval, [Tessera](https://arxiv.org/abs/2610.37080) traces answer evidence from source HTML to reader input across the full English Wikipedia and finds that evidence present on the page often fails to reach the reader intact, worst for tables and infoboxes, which fixed-size chunking separates from the headers and section context that give the cells meaning. Stronger extraction, context expansion and bigger reader budgets all leave the loss in place. Tessera is training-free: it takes the pages behind any ranked list, rebuilds them into fine-grained evidence units that each carry a page title, section path and table headers, selects the relevant units, and packs them at an unchanged token budget. The index, retriever and reader stay untouched, and answer accuracy rises 5 to 6 points on three QA benchmarks for both text and screenshot pipelines, with gains carrying into multi-step agentic search. The finding transfers directly to enterprise RAG over spreadsheets and wiki tables: the unit you rank and the unit you read do not have to be the same object.

FeatureArc's 95% figure and the over-compliance result point at the same missing component, a harness-level check that compares an agent's current work against what it already claimed to finish. Whether the next round of coding-agent harnesses ships cross-stage regression re-tests, or a stop signal built from those six over-compliance markers, will say more about real-world readiness than the next single-shot leaderboard. For text-to-SQL gates, the open question is whether anyone publishes a bypass corpus covering concatenated-string execution across dialects, since that is the class schemagate says its parser cannot close.
