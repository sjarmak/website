31.1% of runs in a new harness benchmark finished their task while failing at least one harness criterion. That figure comes from TraceTrial-Bench, introduced in [Trial by Trace](https://arxiv.org/abs/2610.32285), which scores the harness rather than the model across seven components: context, execution, governance, lifecycle, observability, tools, and verification. The authors built 95 mechanism-oriented tasks with executable or state-based ground truth, ran 4 harnesses and 9 models for 3,420 runs, and got macro-averaged harness scores between 59.8% and 72.0%, a 12-point spread with the model set held constant. The part worth copying is the failure-attribution module, which uses explicit mechanism chains to pin a run's failure to a cause rather than to "the agent." If task success is the only signal you log, a third of the harness problems in this dataset are invisible.

A second paper announced today asks the same question from the other side. [When Agents Fail: Model or Harness](https://arxiv.org/abs/2610.32483) runs four general-purpose harnesses (OpenCode, Codex CLI, Pi CLI, DeepAgents) against four core models, plus two fixed native systems, on six benchmarks covering context management, tool use, long-context planning, multimodal interaction, and artifact handoff: 111 settings, 52,168 trajectories. Its five measures are Valid Completion Rate (did the agent finish normally and hand back something evaluable, correct or not), Model-Harness Fit, Cross-Model Fit, Interaction Residuals, and Token Load counted with failed attempts. Harness rankings change across models and benchmarks, task performance and valid completion favor different pairings, and similar task scores sit on top of distinct execution profiles. OpenCode ranks first on cross-model performance, while DeepSeek V4 Flash Preview holds the highest mean VCR across harnesses on the shared four-benchmark panel. Read together with TraceTrial, the message is that a leaderboard number is a statistic about a pairing, and the harness is now a measurable artifact with its own regressions.

Reliability under broken tools is the third item. [Tool-Calling LLM Agents Under Realistic MCP Faults](https://arxiv.org/abs/2610.32555) builds MCP-Injector, a drop-in middleware that interposes on the Model Context Protocol tool-call path with permanent, transient, and intermittent faults on seedable schedules. The fault distribution is not invented; it is mined from 57,240 issue and pull-request threads across 1,774 open-source MCP repositories, and it skews heavily toward permanent failures. In a 1,350-cell experiment crossing two gpt-oss sizes (20B and 120B), three agent stacks (a custom plan-and-execute loop, OpenAI Agents SDK, LangChain), and three fault conditions, task-completion score drops 60%, from 8.08 to 3.23 out of 10. The 120B model retains no larger share of its fault-free score than the 20B (p = 0.96), and its completion rate under faults is 91.1% against 95.6%. The stacks differ in how much damage they absorb, which places the remedy in framework-level error handling rather than in parameter count.

Knowing when to stop is the next one, and it has the sharpest single statistic of the day. [ImpasseBench](https://arxiv.org/abs/2610.31895) injects twelve realistic environment blockers into otherwise solvable repair tasks and marks, in each trajectory, the step at which the collected evidence became sufficient to conclude that only outside help could restore progress. Across eight frontier models and 19,371 trajectories, nearly every run that needed help gathered that evidence within a few steps, a third exhausted their budget anyway, and every unsafe request the authors detected came after the sufficiency point. An escalation tool cuts budget exhaustion from 34.0% to 6.7%, and an external monitor for models that ignore the tool nearly triples task success once the environment is restored. The remaining gap is the handoff itself: escalation tickets reliably name the blocker but omit the agent's own progress and verification status, so the human picks up a report that says what broke and not what was done.

[Compact-Bench](https://arxiv.org/abs/2610.31710) measures what context compaction costs a long-horizon coding agent, isolating the effect of a single history replacement by pairing full-history and summary-only continuations from the same repository state. It covers 35 SWE-bench repairs, 146 agentic sessions, 106 production compaction chains, and 14 summarizer backbones. Stable damage ranges from 5% to 64% of the 22 full-history successes; Claude Opus 4.8 preserves the most repairs and DeepSeek-Flash damages the most. With Kimi-K3 as the summarizer, the Kimi Code prompt preserves 19 of 22 continuations, while the Claude Code prompt retains the most recurring details at 15.0%. The number that should change how people build compaction: LLM summaries retain at most 16.0% of recurring details, mechanical extraction retains 79.1%, and production summaries hold 15.7% at the first boundary. One repair is damaged by 13 of 14 backbones, another by all five prompts. Retaining relevant information and retaining the progress needed to finish turn out to be different properties.

On orchestration, [Mining the Design Space of Multi-Agent Workflows](https://arxiv.org/abs/2610.31709) treats discarded optimizer trajectories as data. The authors rerun AFlow's MCTS optimizer across six composable operators and 26 deterministically verified Enigmata tasks, keep every intermediate round, and end up with 28,568 executable workflows. A sandboxed AutoResearch loop then mines orchestration code and prompt templates under an L0-penalized validation objective and tests candidate principles on held-out searches, 300 feature-mining trials in all. Three effects survive: workflows that open with independent solvers and one-shot aggregation (Star-first) perform worse (Δ = −0.045); persistent shared documents beat debate (Δ = +0.135); and prompt specificity plus placeholder-based context routing yield Δ = +0.118, on par with picking the communication structure at all. Most of the public argument about multi-agent design has been about topology. The prompt-routing effect is the one with the same magnitude and far less attention.

The governance item today is a product, not a paper. Google's Data Agent Kit reached general availability, reported by [InfoQ](https://www.infoq.com/news/2026/10/data-agent-kit-ga/?utm_campaign=infoq_content&utm_source=infoq&utm_medium=feed&utm_term=global): free, open source, MCP tools into more than fifteen Google Data Cloud services plus 37 Apache-2.0 skills, running inside Antigravity, Claude Code, Codex, Cursor, and VS Code-compatible editors. It ships two guardrails that should not be confused. The accidental-data-loss-prevention skill opens with "STOP AND VERIFY" and asks the agent to get consent before DROP TABLE, TRUNCATE, DELETE without a WHERE clause, production bucket deletions, project deletes, or KMS key destruction; nothing enforces it. The enforced control is an IAM deny policy on the MCP tools.call permission conditioned on the tool's isReadOnly attribute being false, applicable at organization, folder, or project level, with the user's identity propagated so row and column security applies to what the agent reads. Two caveats from the article: blocked tools still appear in the tool list, so the agent discovers the denial only on invocation, and the controls cover Google Cloud MCP servers only. Ankit Dongre's objection is the one that connects back to the fault-injection paper: IAM and dry runs do not tell you whether a timed-out write committed, and the tool results carry no idempotency key, commit status, or rollback handle. That is the exact information an agent needs when the permanent-heavy fault profile from the MCP study hits a write path.

What to watch: whether any harness vendor reports TraceTrial or VCR numbers for its own releases, whether MCP servers start returning commit status as a first-class field, and whether compaction implementations move toward mechanical extraction of recurring state now that the 16% versus 79% gap is on the record.
