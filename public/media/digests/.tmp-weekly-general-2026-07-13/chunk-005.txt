And there was a nice bit of connective data here, because the Pragmatic Engineer newsletter ran some interesting stats out of Cursor about how AI coding is actually being used at scale, the kind of usage numbers that are hard to get from the outside. The short version of all of it is that agent usage inside these tools is climbing fast enough that the tools are now being reshaped around managing many agent runs, not around single completions. The features tell you the same thing the stats do. This is turning into fleet management.

JetBrains shipped something their users have been openly asking for, by JetBrains's own account, for over a year. ReSharper, in the 2026.2 release, now has a real .NET debugger inside VS Code and Cursor. Built on the very same debugging engine that powers Rider, which is JetBrains's full standalone IDE. Now if you're not in the .NET world this might sound mundane, but stay with me, because it's a good illustration of where a lot of the real value still is. Debugging has been the single standing reason a lot of .NET developers couldn't leave the heavy full IDE for the lighter VS Code-family editors. You could edit your code there just fine. You couldn't really debug it there. So people stayed in the big IDE for that one capability. This release is the first version of closing that gap, and it's a reminder that an enormous fraction of the value being created in this space is still, unglamorously, making the tools people already use work in the places they actually want to work. Not every advance is a new model. Some of the most valuable ones are a debugger finally showing up where you needed it.

And GitHub published something I genuinely appreciated, an honest engineering retrospective titled, better tools made Copilot code review worse, here's how we actually improved it. Pay attention to this one if you build any kind of agent tooling, because the finding is counterintuitive and it's exactly the sort of hard-won lesson that usually stays locked inside a company and never gets written up. Their finding was that giving their code-review agent more tools actually degraded the quality of its reviews before it made them better. More capability, worse output. And the fix, this is the good part, wasn't about making the underlying model smarter. It was about constraining what the model reached for, narrowing the tool surface so the agent stopped distracting itself with options it didn't need. Think about how much that cuts against the current instinct. Everybody right now is bolting more and more onto their agents, more MCP servers, more tools, more context, on the assumption that more is more. And GitHub, at scale, on a real product, found that past a point the extra tools made the thing dumber, and that curation beat accumulation. The harness matters more than the size of the toolbox. That's one of the most practically useful sentences anyone published this week.

That GitHub piece is a natural bridge into what I think was actually the deepest theme of the week, which is code review, and more broadly, what happens to the craft of software when the machine writes most of the code. Because that tension is now showing up everywhere you look.
