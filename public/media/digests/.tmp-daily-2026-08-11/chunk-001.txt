The second benchmark from the same day is SWE-RPG, and it attacks the other half of the problem. Existing repository-level benchmarks score the final patch. Pass or fail. Which means when a run fails you learn nothing about where it went off the rails. SWE-RPG has a hundred sixty-three tasks from thirty-one Python and Java repositories, a hundred thirteen bug fixes and fifty feature additions, and it pairs the executable patch evaluation with validated ground truth for two intermediate stages: requirement clarification, and implementation planning. So you can diagnose a trajectory retrospectively and say, this run had the requirements right and blew the plan, or this run never recovered the requirement at all. They ran Claude Code, Codex, and OpenCode across six model backends including Claude Sonnet 5 and GPT-5.6-Terra. Average resolved rate, thirty-one point five percent.

But the diagnosis is the real result. Implicit requirement recovery, meaning everything the user meant and did not say, accounts for somewhere between twenty-four point five and forty-six percent of agent runs depending on configuration. So a quarter to nearly half of the failures happen before any code gets written. The agents are not primarily failing at writing code. They are failing at working out what was actually being asked. Which is the same failure as the retries incident, just measured at scale instead of narrated by one person who had to explain four duplicate jobs to another team.

There's a third study I want to put next to those, called MSEval, which came out overnight. This one holds the model fixed and varies the organizational structure instead. Ten authentic full-stack projects across ten domains. Ten different collaboration topologies, with agents coordinating on periodic sync intervals and deploying through real CI/CD pipelines rather than a simulated environment. A hundred runs, scored by an automated grader that probes the running implementation and measures three things jointly: functional success, latency, and prefix-cached token cost. So it's tracking what the thing costs to run, not just whether it finished.

The headline is that changing the topology alone, same task, same model, shifts scores by more than thirty points and doubles wall-clock time. Organizational structure rivals model capability in determining the speed, cost, and quality trade-off. And the specific finding is one a lot of teams should hear: structured pipelines converged fastest and at the highest quality, while heavy managerial oversight degraded performance. Heavy managerial oversight is exactly what most people reach for when their swarm starts producing garbage. Add a supervisor agent, add a reviewer above the reviewer. According to this data that's the wrong direction, and the fix is a tighter pipeline rather than a taller hierarchy.

The second practitioner story from the last day is about verification, and it's short. An agent rewrote the pagination logic in a data-sync job and reported, quote, done and tested. CI passed, because the test fixture only had one page of data in it. The next morning the sync died in staging after a hundred records, because the cursor never advanced. Then, to make it worse, the developer had the same agent review its own pull request, and it approved with enthusiasm. His conclusion is blunt: having the model that wrote the code review its own code is useless, because it grades its own work with exactly the same blind spots that produced the bug. Asking an agent to double-check itself gets you a confident yes.
