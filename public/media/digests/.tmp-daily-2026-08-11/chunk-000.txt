The sequence went like this. He gave the agent a one-line instruction. The agent put backoff around the shared request helper, the file at source, lib, http dot ts. That is a completely fair reading of the instruction. The problem is that the job-creation POST also goes through that same helper, and that endpoint has no idempotency key. The queue was slow that week, so some of those calls timed out on the client side after the server had already committed the write. First attempt plus three retries, and now there are four identical jobs sitting in staging. Those jobs fan out webhooks, so a shared consumer downstream received the same payload four times, and the team that owns that consumer noticed the problem before the author did. What I found interesting is the second finding: blast radius cues barely changed how often an agent acted out of bounds. Target ambiguity is what degraded the behavior. Telling the agent that something is dangerous doesn't help nearly as much as telling it precisely which call sites are in scope. His practice now is writing that down before there is any code: which call sites are in bounds, what should be true when the agent stops, and what his open questions are, answered up front. He notes that review does not catch this class of problem, because target selection is invisible once every line looks reasonable on its own.

Now, hold that next to two benchmarks that both landed yesterday, because they're going after the same gap from the research side.

The first is SWE-Bench ProMax. A hundred and seventy expert-curated refactoring instances, drawn from real commits across seven languages: Python, Java, TypeScript, Go, C, C plus plus, and Rust. These are big tasks on purpose. Eleven point four modified files per instance on average, two hundred sixty-one point six lines of code, coordinated changes that have to preserve behavior across a repository. The best frontier model, run under two different agent scaffolds, resolves forty-one point two percent. That number is useful, but the motivation section is the part I'd actually read. The authors cite an audit finding that nearly sixty percent of the unsolved instances in SWE-bench Verified contain flawed tests. Some are overly narrow, meaning they reject a solution that is correct. Some are overly broad, meaning they check requirements that were never stated in the issue. And on top of that, frontier models can reproduce the gold patches verbatim from training data. So when a model climbs the leaderboard on that benchmark, you genuinely cannot tell what you're measuring. ProMax's answer is expensive and manual: rewrite every issue description from scratch so the specification is unambiguous, hand-review every test suite to strip the narrow and broad tests, and filter out any task that isn't large and cross-file enough to be interesting. That's the tax on a trustworthy benchmark right now, and it's worth naming, because a lot of eval work skips it.
