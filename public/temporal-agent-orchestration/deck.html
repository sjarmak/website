03 / the concepts

Three jobs, three ownersBeads holds the work: a durable graph of tasks, claims, and receipts. Agents do the work their own way, at messy benches. Temporal keeps the running checklist of what already happened, and that checklist is what survives a crash.

Gas City: an orchestrator that hands tracked work to coding agents
04 / the original problem

One task, five owners, seven crash windows

Only the Beads boxes are durable records; every arrow lived in process memory 100 repair jobs firing 850×/hour · one PR poller: 243 lines of Bash, 174 cache files
05 / after the crash

Recovery by conspiracy boardAfter a crash, the restart could launch a second agent, wait for a process it could no longer contact, or reconstruct the procedure from stale claims, half-delivered mail, and whatever process happened to still be alive. I ran versions of all three.

The work record survived in Beads; the procedure existed only as clues
06 / two kinds of recovery

Two recovery models, one system

Nondeterministic idempotence

  • A new agent may find another valid route
  • Right for the coding work itself
  • Stays with Beads and Gas City

Deterministic durable replay

  • Ordering and acknowledgement stay exact
  • Right for claims, receipts, and handoffs
  • Becomes a Temporal Workflow
The agent chooses its route through the work; the promises around it replay exactly

Owns

Event dedupe, Activity identity, cancellation, and the completion policy.

Excludes

Process launch, file edits, model calls, clocks, and the store.

Persists

Every decision lands in Event History, so a replacement Worker replays it.

Stable identity lives in the claim token and session binding; the formula-derived Activity ID is for observability

One kill, two sessionsThe coordinator dies; the agent keeps working. The restart sees claimed work with no recorded session and launches a replacement. The witness pane reads agent procs 2, sessions 2, and the older attempt lands a stale receipt over the current one.

14 / with Temporal

The Worker dies. The agent does not.Two kills: one after a heartbeat checkpoint, one before any checkpoint exists. Both retry windows read agent procs 2, sessions 1: the retry re-binds the session that is already working. Both arms end with one session and one fenced receipt.

The pause is Temporal waiting out the heartbeat timeout · same fixture, same kill, different orchestrator
15 / the invariants
SessionsExactly one session created per arm, across two attempts.
ReceiptsOne terminal receipt; a completion carrying the stale claim token failed closed.
ResolverArm two called it twice; it returned the existing session instead of minting one.
RetryAttempt two finished the work, under the same Activity identity.
TestsDuplicate delivery against a real dev server schedules one Activity; the replay gate rejects a planted nondeterministic Workflow.

16 / limits and cost

What Temporal did not solve

01

Not exactly-once

A Worker can die after an external call succeeds. Slack, GitHub, and the agent still need their own idempotency.

02

Not correctness

One live run retried an invalid envelope every fifteen minutes, exactly as instructed, until I rolled the change back.

03

Not free

Replay discipline, compact histories, and two durable records to reason about. Not every job justifies that.

The maintenance pilot stayed cron plus a lock; a crash there strands no procedure
17 / where it stands
Running today

In production

Durable result delivery and exact acknowledgement run continuously in my live installation. The larger claim-and-launch path is built, tested against the adapter contract, and staged for rollout.

What transfers

Promises vs work

Workflows own promises; Activities own work. Stable identity turns a retry into a continuation. Choose which continuity the system refuses to lose.

Teaching it

Failure first

Start from the failure, run the demo, then read the code. The case study, the annotated source reader pinned to real revisions, and the hashed evidence bundle follow that same order.

Same-host recovery proven; cross-host reattachment is the next milestone
18 / the takeaway

Choose which continuity the system refuses to lose

The agent keeps its freedom to find the route. The work record keeps the facts. Temporal keeps the promises: who owns the work, what remains outstanding, when a handoff is complete, and what must happen next.
