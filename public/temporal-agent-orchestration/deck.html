04 / two kinds of recovery

Two recovery models, one system

Nondeterministic idempotence

  • A new agent may find another valid route
  • Right for the coding work itself
  • Stays with Beads and Gas City

Deterministic durable replay

  • Ordering and acknowledgement stay exact
  • Right for claims, receipts, and handoffs
  • Becomes a Temporal Workflow
The agent chooses its route through the work; the promises around it replay exactly

Owns

Event dedupe, Activity identity, cancellation, and the completion policy.

Excludes

Process launch, file edits, model calls, clocks, and the store.

Persists

Every decision lands in Event History, so a replacement Worker replays it.

Stable identity lives in the claim token and session binding; the formula-derived Activity ID is for observability

Claim fence

The Activity claims the exact work generation; a stale token fails closed.

Start-or-attach

The resolver returns the session that owns the claim instead of minting another.

Checkpoint

Heartbeats carry a compact cursor, so the retry resumes instead of restarting.

09 / with Temporal

The Worker dies. The agent does not.Two kills: one after a heartbeat checkpoint, one before any checkpoint exists. Both retry windows read agent procs 2, sessions 1: the retry re-binds the session that is already working. Both arms end with one session and one fenced receipt.

The pause is Temporal waiting out the heartbeat timeout · same fixture, same kill, different orchestrator

11 / the canary that failed

The first result-delivery canary failed

The path under test delivers a finished result and waits durably until that exact outcome is acknowledged. Its first bounded live run hit the promotion gate and exposed four real defects.

ContentionConcurrent notifications fought over a shared mail store.
PhantomCorrelation metadata named a Workflow that did not exist.
ConfusionAn observer mistook a completed step for its still-running source task.
SilenceLegitimate completions closed real work without an OutcomeReady envelope.

The Mayor rolled back to shadow, repaired the path, and recovered the stranded results. Temporal made each failure specific and observable rather than silent. That is what the canary and the promotion gate were for.

The repaired path now runs continuously in production
12 / limits and cost

What Temporal did not solve

01

Not exactly-once

A Worker can die after an external call succeeds. Slack, GitHub, and the agent still need their own idempotency.

02

Not correctness

One canary retried an invalid envelope every fifteen minutes, exactly as instructed, until I rolled it back.

03

Not free

Replay discipline, compact histories, and two durable records to reason about. Not every job justifies that.

The maintenance pilot stayed cron plus a lock; a crash there strands no procedure
13 / where it stands
Running today

Shadow to enabled

Result delivery and exact acknowledgement run continuously. Work claiming and agent launch stay in shadow behind one bounded canary: one claim, one session, one fenced receipt.

What transfers

Promises vs work

Workflows own promises; Activities own work. Stable identity turns a retry into a continuation. Choose which continuity the system refuses to lose.

Teaching it

Failure first

Start from the failure, run the demo, then read the code. The case study, the annotated source reader pinned to real revisions, and the hashed evidence bundle follow that same order.
