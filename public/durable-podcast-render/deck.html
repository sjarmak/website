04 the fit 4:00 to 5:30

Why Temporal fits here

Durable progress

Each completed chunk Activity is an event in server-held history. Progress survives every process that touched it.

Activity retries

A retryable provider error is a policy decision, not hand-rolled loop code. Only the failed chunk retries.

Replay after worker loss

A replacement worker replays history and continues mid-render, no application recovery script.

Status during work

The API projects Workflow state into completedChunks 6/8 while the render runs.

All four without replacing the domain stores: PostgreSQL and object storage keep owning what they already own.

07 the mechanics 8:15 to 9:15

The Workflow coordinates metadata, the API turns async

workflow renderPodcast(input) {
  plan = await activity.loadAndPlan({ renderKey, transcriptRef,
    expectedTranscriptHash, config })
  for (chunk of plan.chunks)
    chunks.push(await activity.renderChunk({ renderKey,
      transcriptRef, chunk, config }, retryPolicyForProvider))
  assembled = await activity.stitchChunks({ renderKey,
    format, stitcherVersion, chunks })  // ffmpeg, not Buffer.concat
  return activity.publishRender({ renderKey, planHash,
    chunks, assembled })
}

10 the caveat 15:30 to 17:00

At-least-once execution leaves an external ambiguity window

If a provider accepts a request and the worker dies before recording completion, Temporal may run the Activity again. A deterministic object key prevents duplicate stored chunks. It does not prove that a provider charged once or generated audio once. This design does not claim exactly-once billing.

Object storage

Deterministic keys plus checksum validation make the write ambiguity recoverable.

PostgreSQL

Unique renderKey and conditional upsert: repeated publication converges on one row.

Provider

Ambiguous without a documented idempotency key and request-status lookup. v1 reports and measures it, never hides it behind the cache constraint.

Provider selection

Idempotency and status lookup are correctness properties, not only voice quality and latency.

11 scope 17:00 to 18:15

Version one stays sequential and single voice

In

Long-form sanitized transcripts, one voice, one concrete provider model, sequential chunks, MP3 or WAV only after the stitcher has a validated path for each format.

Sequential keeps rate-limit behavior legible and the event history readable on stage.

Out

Multi-voice parsing, parallel rendering, live streaming, mid-render transcript edits, automatic provider failover, user-driven partial regeneration.

No migration of existing cached files: a current cache hit stays on the legacy path; new asynchronous renders use the versioned identity.

Assembly is format-aware ffmpeg with container validation. Never Buffer.concat: correctness includes seeking, duration, headers, and playback across chunk boundaries.

Stage 3Workflow and worker Sequential Workflow, bounded timeouts, classified retries, progress queries, explicit versioning
Stage 4Async API Start and status routes, duplicate-start behavior, stable error model; synchronous route untouched

The synchronous route becomes a compatibility wrapper only after consumers are measured and a deprecation decision is made.
